# 要件定義ドキュメント作成スキル

docs/requirements/ 配下の 3 ドキュメントを、ユーザーへのヒアリングを通じて作成・更新する。

## 手順

### 1. 現状確認

- docs/requirements/ 配下の 3 ファイルを読み、記入済み箇所と `{/* TODO` コメントの残り箇所を把握する
- 既に記入済みの内容は上書きせず、追記・更新の形で扱う

### 2. ヒアリング

AskUserQuestion を使い、以下の順でヒアリングする。1 回の質問は 4 項目以内に抑え、複数ラウンドに分ける:

1. **プロジェクト概要**: 背景・課題、目的と成功基準(何をもって成功とするか・確認方法)、スコープ(対象/対象外)、予算・納期の制約、変更管理手順
2. **体制**: 顧客側・自社側の登場人物と役割(利用者・運用担当・情報システム・法務など、要求の発生源になる関係者を漏らさない)
3. **要求**: 誰が・何をしたいか・なぜか(5W1H)。優先度(MoSCoW)
4. **非機能・制約**: 利用人数・データ量・稼働時間帯・セキュリティ要求、守るべき法令・契約・社内規則

自由記述が必要な質問(背景の詳細など)は AskUserQuestion ではなく通常の対話で確認する。

ヒアリングでは要望・要求・要件を区別する(`.claude/rules/workflow.md` 参照):

- 要望(「〜を楽にしたい」等)は顧客の言葉のままヒアリングメモに残し、「なぜ必要か」を確認して要求へ整理する
- 手段で語られた要求(例: 「PDF で出力したい」)は目的を確認し、既存の手順・帳票・承認をそのまま前提にしてよいか、システム化以外の手段(業務手順の変更・運用対応)で足りないかを尋ねる
- 要求同士が矛盾する場合は、その場でトレードオフを提示して優先度を確認する
- 推測で補った内容は確定事項として書かず、状態を「候補」にするか TODO として残し、ユーザーに確認する

### 3. ドキュメント作成

以下の順で作成し、`.claude/rules/documentation.md` の書式・ID 採番規則に従う:

1. `docs/requirements/01-project-overview.mdx` — 背景・目的・成功基準・スコープ・体制・マイルストーン・変更管理
2. `docs/requirements/02-user-requirements.mdx` — 要求一覧(REQ-xxx。発生源・根拠・優先度・状態を記載)・受け入れ基準・未確定事項・変更履歴
3. `docs/requirements/03-system-requirements.mdx` — 機能要件(FR-xxx)・非機能要件(NFR-xxx)。各要件に対応する REQ と検証方法を必ず紐付ける

- 要求一覧を確定する前に、02-user-requirements.mdx の「要求分析の確認観点」で各要求を点検する
- 要件文は `.claude/rules/documentation.md` の「要件文の書き方」に従い、検証可能な形で書く
- 状態が「合意」の要求を変更・取り下げする場合は、変更履歴に変更理由と影響範囲を記録する
- ヒアリングで得られなかった箇所は `{/* TODO: ... */}` コメントを残す
- テンプレートの「例:」で始まる記入例は、実際の内容に置き換えたら削除する

### 4. 完了報告

- 作成・更新したファイルと、残っている TODO・未確定事項を一覧で報告する
- 次のステップ(TODO の解消 or `/design` への移行)を提案する
