# ドキュメント作成ワークフロールール

## 作成順序

ドキュメントは必ず上流から下流の順で作成する:

1. **要件定義** (docs/requirements/) — プロジェクト概要 → 要求定義 → 要件定義
2. **設計** (docs/design/) — 要件定義の FR/NFR を入力とする
3. **見積もり** (docs/estimate/) — 要件定義と設計を入力とする

下流のドキュメントを作成する前に、上流ドキュメントに重大な `{/* TODO */}` が残っていないか確認し、残っている場合はユーザーに知らせる。

## 要望・要求・要件の区別

IPA「AI時代の要求管理ハンドブック」の整理に従う:

- **要望**(望み・困りごと)をそのまま要求・要件にしない。背景にある目的を確認し、**要求**(実現したいこと = REQ)として整理してから、**要件**(実装・評価できる事項 = FR/NFR)へ具体化する
- 要求には発生源と根拠(目的)を記録する。根拠を書けない要求は、目的と手段が混ざっていないか確認する
- すべての要求をシステムで実現するとは限らない。業務手順の変更・運用での対応と比較したうえで、システムが担う範囲だけを要件化する
- ヒアリングで得ていない内容を推測で補った場合は、確定事項として書かず、候補であることを明示してユーザーに確認する

## トレーサビリティ

- 機能要件(FR)・非機能要件(NFR)には必ず対応する要求 ID(REQ)を紐付ける(「—」のまま残さない。法令・社内規則が発生源の場合も REQ として採番する)
- 設計上の判断(画面・技術選定・アーキテクチャ)には根拠となる FR/NFR を紐付ける
- 見積もり WBS の各タスクには対応する要件 ID を紐付ける
- 存在しない ID を参照しない(/doc-review で検出される)

## 上流変更時の下流更新義務

上流ドキュメントを変更したら、同じ作業の中で下流への影響を確認する:

- 要求・要件の追加/変更 → 設計(画面一覧・アーキテクチャ)と見積もり(WBS)を確認
- 設計の変更(技術・構成) → 見積もり(開発費用・運用費用)を確認
- 影響がある下流ドキュメントはステータス行を `draft` に戻し、影響箇所に TODO を残すか即時更新する

## 変更管理

状態が「合意」の要求、またはそれに紐づく要件を変更するときは、変更レベルに応じた位置まで戻る:

| 変更レベル | 戻る位置 |
| --- | --- |
| 目的・成功基準の変更 | docs/requirements/01-project-overview.mdx から再整理 |
| 要求・業務の変更 | docs/requirements/02-user-requirements.mdx から再整理 |
| 要件・実現手段の変更 | docs/requirements/03-system-requirements.mdx から再整理 |

- 変更内容・変更理由(環境変化 / 学習 / 不備の訂正)・影響範囲を docs/requirements/02-user-requirements.mdx の「変更履歴」に記録する
- 要件は妥当で実装が満たしていないだけの場合は、要件を変更せず不具合として扱う

## 見積もりの原則

- 単価・工数は docs/estimate/01-development-cost.mdx の単価表を使う
- 前提条件・除外事項を必ず更新する(スコープが変わったら特に)
- 金額を勝手に確定しない — 工数(人日)の算出まで行い、単価・バッファ率の最終判断はユーザーに確認する
